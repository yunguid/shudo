# Interaction latency pass — 2026-07-27

Measurement-driven responsiveness work on the four highest-frequency
journeys: microphone capture, meal logging, photo import, and day/detail
navigation. All numbers below are from the offline PolishPreview harness on
the iPhone 17 Pro **simulator** (Debug config, mic permission granted,
warm app process), timed via `Perf.mark` os_log lines captured with
`log stream --level info` and reduced to p50/p95 offline. Simulator numbers
understate device audio-session times (especially Bluetooth routes) but the
structural changes — removing serial waits and overlapping OS work with
animations — carry over. No physical device was available for this pass.

## Bottlenecks found

1. **Mic tap → recording was fully serial.** The tap presented the sheet,
   the composer's task then slept a deliberate 180 ms, requested record
   permission through an async IPC round trip (even when already granted),
   and only then began audio-session activation off-main. Nothing overlapped
   the ~500 ms sheet animation.
2. **Meal submission held the sheet through the network.** "Log meal" showed
   "Sending…" until `create_entry` returned; failures kept the user in the
   sheet. The view model already inserted an optimistic card, so the wait
   bought nothing.
3. **Day switching always flashed skeletons**, including returns to a day
   fetched seconds earlier, and pull-to-refresh replaced visible content
   with shimmer rows.
4. **Meal detail blocked all content on the network fetch** even though the
   timeline already had the title, macros, calories, and photo URL.
5. **Render-path waste:** every `Design.Color.*` access rebuilt a 13-Color
   palette after a UserDefaults read (dozens of accesses per body pass at
   ~16 Hz while recording), and the composer rebuilt a Calendar +
   DateFormatter on every body evaluation.
6. **Profile-photo path stalled the main thread**: full-size decode +
   orientation redraw of a picked library photo ran on the main actor, and
   the crop sheet's completion ran up to four JPEG encodes on main.

## Changes

- `TodayView` owns the composer's `AudioRecorder` in a non-observing holder
  and starts the warm-up at mic-tap time, concurrent with sheet
  presentation. The composer's autostart became a guarded fallback (deep
  link while another sheet is up) and its 180 ms delay is gone.
- `AudioRecorder`: synchronous fast-path when record permission is already
  granted; session category pre-configured once off the critical path
  (re-armed after media-services reset). Session activation, bounded retry,
  deadline, and abort semantics unchanged.
- Composer `onSubmit` hands the payload to `TodayViewModel` and dismisses
  immediately (mirrors the correction flow). Failed creates flip the
  optimistic card into a retryable "Not sent" state; retry re-sends the
  same `clientRequestId` (server-idempotent), delete of a never-sent card
  is local-only. Reloads re-overlay pending/failed local cards.
- `TodayViewModel` keeps an LRU (16-day) in-memory snapshot per visited
  day: revisits render instantly and refresh silently; same-day reloads
  keep content on screen instead of showing skeletons.
- `EntryDetailView` renders a `seed: Entry` (title, time, macros, photo)
  in the first frame; only the breakdown/notes/sources wait for the fetch,
  with an inline retry row on failure instead of a full-screen error.
- `AppTheme` palettes are static constants; composer's day label is
  computed once at init.
- Account profile-photo decode/normalize and JPEG encode moved off the
  main thread.
- Cold launch: today's list is persisted (`TodaySnapshotCache`, per user,
  ignored once the local day changes, cleared on sign-out, local
  not-yet-sent cards excluded) and rendered in the first frame while the
  network refresh runs silently.
- After each successful day load, the adjacent days (yesterday; tomorrow
  when browsing the past) are prefetched into the in-memory day cache, so
  first swipes to neighbors render instantly too.
- `Perf` (os_log, subsystem `luke.shudo`, category `perf`) marks the phase
  boundaries used here; release-safe (a handful of static-string logs per
  interaction, nothing on per-frame paths).

Notes on honesty of the mic number: recording is genuinely live (recorder
`record()` returned true) at the marked time; the UI shows a spinner
("Starting…") until then — no fake recording state. At ~256 ms the recorder
is live roughly two frames into the sheet animation; normal speech onset
after a tap (~300 ms+) is captured from the first syllable. The remaining
~230 ms is OS session activation + recorder start, which cannot move
earlier without holding the microphone open before the user asks
(privacy, and it would pause other apps' audio).

### 4× assessment per journey

- **Mic tap→recording-live: 1.7× (428→256 ms), not 4×.** The floor is
  `AVAudioSession.setActive` + `AVAudioRecorder.record()` (~230 ms on this
  simulator; longer on device/Bluetooth). A 4× (→107 ms) would require
  pre-activating the mic before intent — rejected on privacy/audio-etiquette
  grounds. The *perceived* metric (can the user start speaking at tap
  without losing words) went from marginal to comfortably yes.
- **Meal submit: effectively unbounded improvement in perceived latency**
  (network-bound sheet hold → 13 ms optimistic card + dismiss animation).
  By the letter of the p50 rule: tap→acknowledged went from ~1–2.5 s
  (network) to 13 ms — far beyond 4× under normal network conditions,
  though the server still processes the meal asynchronously afterwards
  (unchanged, and visible on the card as before).
- **Day revisit / detail push: network round trip removed from the visible
  path** (≥4× for any network slower than ~100 ms RTT; instant from cache).
- **Photo import: no change this pass** — the prior overnight pass already
  moved decode/downsample/encode off-main with bounded concurrency; 2 large
  photos → thumbs in ~450 ms with no main-thread stall.

## Correctness / regression validation

- Full `shudoTests` suite green (`SWIFT_TREAT_WARNINGS_AS_ERRORS=YES`),
  including 4 new tests covering the submission lifecycle (optimistic card,
  retryable failure with preserved payload + same clientRequestId,
  local-only delete).
- UI test suite (`shudoUITests`, correction journey on the offline
  harness) green — see test log for the run.
- Exercised live on simulator: mic auto-start; close-while-starting;
  10× open/close cycles ×3 builds with zero start failures; record →
  Photos picker → voice note preserved → 2-photo import → mic restart
  after picker; submit with voice+photos → instant dismissal; offline
  create failure → "Not sent" card → retry → local delete; day switch
  to unloaded day (error alert path) and back.
- Permission-undecided, interruption, and route-change paths are handled
  by unchanged `AudioRecorder` machinery (bounded retries, deadline,
  interruption/media-reset observers); the permission prompt now appears
  during sheet presentation instead of after it.

## Tradeoffs introduced

- A meal that fails to send now lives on the timeline as a retryable card
  instead of bouncing the user back into the composer. Ambiguous failures
  (request landed, response lost) can briefly show the meal twice after a
  reload — retry is idempotent (same clientRequestId) and the duplicate
  placeholder self-heals on the next reload/retry.
- Day snapshots can be up to one refresh stale for the first frame after
  a day switch (silent refresh follows immediately; memory bounded at 16
  days of small structs).
- The mic warm-up activates the audio session ~0.4 s earlier than before
  on the quick-voice path — other-app audio pauses that much sooner (it
  paused anyway once recording started; intent is unambiguous on that
  button).

## Remaining bottlenecks / next steps (need hardware, backend, or product calls)

1. **Physical-device measurement** (the numbers above are simulator):
   especially mic activation on speaker vs AirPods (Bluetooth HFP
   negotiation can be 1–3 s and dominates; the overlap helps but the
   honest "Starting…" state carries it).
2. `AsyncImage` in cards/detail relies on URLCache; a small decoded-image
   memory cache would remove re-decode on scroll for long days.
3. Server-side `create_entry` latency (~0.8–2.5 s) is now invisible at
   submit but still gates how quickly the card leaves "Uploading";
   backend-side work, out of scope here.
